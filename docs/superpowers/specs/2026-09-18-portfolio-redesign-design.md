# Редизайн jeezdredd.github.io — дизайн-документ

Дата: 2026-09-18
Статус: на ревью

## 1. Цель

Переработать сайт-визитку так, чтобы он перестал читаться как сгенерированный шаблон, и превратить его в живую приборную панель: состояние проектов, метрики, журнал инцидентов и телеметрия посетителей. Упрощать функциональность нельзя — объём растёт, а не сокращается.

## 2. Диагноз текущего состояния

Сайт содержит набор признаков, по которым узнаётся генерированное портфолио:

- фальшивый терминал-лоадер, печатающий выдуманный вывод
- glitch-анимация на имени, typed-эффект в hero, частицы на canvas, курсор-трейл
- бегущая строка иконок стека
- секции, пронумерованные `01`–`05`
- пульсирующий бейдж «Available for hire»
- текст с оборотами вида «There's something deeply satisfying about turning a vague idea into a working system»
- `ambient.mp3` весом 4.7 МБ — в сто раз больше, чем весь остальной сайт

Отдельно — работающая проблема безопасности: адрес Discord-вебхука лежит открытым текстом в `script.js` публичного репозитория. Любой посетитель может его прочитать и слать в канал произвольные сообщения или заспамить до срабатывания лимитов. Расширять логирование поверх этого нельзя.

## 3. Принятые решения

Все решения приняты в ходе брейншторма с визуальными макетами. Макеты лежат в `.superpowers/brainstorm/41634-1789754026/content/`.

| Решение | Выбор |
|---|---|
| Визуальное направление | Гибрид instrument panel + brutalism |
| Композиция | Микс трёх компоновок: split-hero, заявление слева, статус-заголовок справа |
| Имя | Всегда полностью, `SEVASTYAN CHE`, без сокращения до `S.CHE` |
| Бренд-акцент | Ultramarine `#2B2BFF` |
| Правило палитры | Статусы приглушены, бренд — единственный насыщенный цвет |
| Лоадер | Синяя плита с пробами схлопывается в вертикальную линейку hero |
| Язык интерфейса | Английский, плоский фактологичный тон |
| Правило движения | Анимация разрешена, только если несёт информацию |
| Источник статусов | GitHub Actions cron → `status.json` в репозитории |
| Предмет панели | Три блока: SERVICES (живое), BUILD (GitHub API), ARCHIVE (снятое с эксплуатации) |
| Организация кода | Vanilla + ES-модули, без сборки для продакшена |

### 3.1 Поправка к премисе, 2026-09-19

Исходный замысел строился на «пять живых сервисов». Проверка показала, что это неверно: Tandem, P2P Learning, Social Platform и остальные сняты с хостинга и являются архивными. Живой проект один — `prooflayer.cloud`, и на момент проверки он отдаёт `HTTP 530` с заголовком `server: cloudflare`, то есть Error 1033: туннель Cloudflare не подключён, коннектор на стороне origin не отвечает.

Панель из одной красной строки не выполняет задачу. Поэтому предмет наблюдения расширяется: к живым сервисам добавляется блок BUILD на данных GitHub API, которые существуют независимо от того, задеплоен проект или нет. Ничего не выдумывается и ничего не поднимается ради картинки.

Модули грузятся через `<script type="module" src="js/main.js">`. Сборки для продакшена нет — GitHub Pages отдаёт файлы как есть. Строка в футере «built with vanilla HTML/CSS/JS, no framework» остаётся правдой: npm появляется только как dev-зависимость для тестов и в продакшен-бандл не попадает.

### 4.2 Внешние компоненты

**GitHub Actions cron.** Раз в 5 минут пингует адреса сервисов, измеряет код ответа и время, применяет ручные оверрайды, пишет `status.json` и дописывает `history.json`, коммитит их в репозиторий. Запускается с раннера, поэтому CORS не мешает.

**Cloudflare Worker.** Принимает телеметрию от сайта, проверяет источник, режет частоту, отбрасывает мусор и пересылает в Discord. Адрес вебхука хранится в секрете Worker и в репозиторий не попадает.

**Worker KV.** Счётчик посетителей и дедупликация. Без хранилища цифра в футере будет врать.

## 5. Дизайн-система

### 5.1 Цвет

```
--ground      #08090A
--ink         #E9EDEF
--muted       #8B949E
--dim         #5A636A
--line        #1C2024
--brand       #2B2BFF
```

Ультрамарин занимает ровно четыре места на странице: вертикальная линейка hero, заливка одного слова в заголовке, главная кнопка, активный пункт меню. Появление в пятом месте считается дефектом.

Плита лоадера — единственное исключение и одновременно объяснение правила: цвет один раз занимает весь экран, затем схлопывается в линейку hero и дальше живёт только в этих четырёх местах. Именно поэтому схлопывание, а не уезжание за край: зритель видит, откуда взялась линейка.

Светлая тема — полная инверсия, а не осветление: белая земля, чёрные линейки 4 px, статусные цвета затемняются до контраста не ниже 4.5:1 на светлом.

### 5.2 Состояния сервиса

Восемь состояний. У каждого свой знак, а не только цвет — сайт обязан читаться при дальтонизме и в чёрно-белой печати CV.

| Ключ | Подпись | Знак | Цвет | Кто ставит |
|---|---|---|---|---|
| `operational` | OPERATIONAL | ● | `#56A868` | проба |
| `degraded_performance` | DEGRADED PERFORMANCE | ◐ | `#B8893D` | проба |
| `partial_outage` | PARTIAL OUTAGE | ◑ | `#C2683C` | вручную |
| `major_outage` | MAJOR OUTAGE | ✕ | `#B5524A` | проба |
| `under_maintenance` | UNDER MAINTENANCE | ◌ | `#5B7A99` | вручную |
| `third_party_error` | THIRD-PARTY ERROR | △ | `#8A6DA8` | вручную |
| `mitigated` | MITIGATED | ◈ | `#6E9E7A`, штриховка 45° | вручную |
| `discontinued` | DISCONTINUED | ◇ / ◆ | `#6E7681` / `#4A5259` | вручную |

`mitigated` рисуется штриховкой, а не заливкой: последствия устранены, корневая причина жива — это другой класс состояния, а не оттенок зелёного.

`discontinued` имеет поле `permanence` со значениями `temporary` и `permanent`. Временный рисуется полым знаком, постоянный — сплошным серым с зачёркнутым названием сервиса. Цвет серый, а не красный, потому что это не авария, а намеренное решение; сигнальные цвета зарезервированы под то, что требует реакции.

### 5.3 Типографика

| Роль | Гарнитура | Размер |
|---|---|---|
| Заголовок hero | Archivo Black | 52 px, `letter-spacing: -0.037em` |
| Заголовок секции | Archivo Black | 17 px |
| Текст и данные | JetBrains Mono 400 | 12 px |
| Служебные метки | JetBrains Mono 400 | 9 px, `letter-spacing: 0.2em` |

Instrument Serif и DM Mono с текущего сайта удаляются.

### 5.4 Движение

Остаётся: смена статуса (перекраска 200 мс), схлопывание плиты лоадера, эквалайзер от реального сигнала, hover и focus, раскрытие карточки сервиса, тикающие часы.

Удаляется: glitch, typed-эффект, частицы, курсор-трейл, бегущая строка, фальшивый терминал, пульсации, fade-up на скролле.

При `prefers-reduced-motion: reduce` остаются только мгновенные смены состояния; лоадер показывается статичной плитой без схлопывания.

Лоадер показывается один раз в сутки на устройство. Факт показа хранится в `localStorage`; при повторном визите страница открывается сразу, без плиты. Жест, повторённый пять раз за вечер, из впечатления превращается в задержку.

## 6. Композиция страницы

1. **Навбар** — `SEVASTYAN CHE`, пункты меню, статус доступности, локальное время, переключатель темы. Липкий.
2. **Hero** — сетка 66% / 34%, разделённая вертикальной линейкой 4 px ультрамарина.
   - Слева: кикер, заголовок в три строки с заливкой одного слова, лид, кнопки.
   - Справа: заголовок-состояние `N OF M OPERATIONAL`, сетка из четырёх метрик, компактный список сервисов.
3. **Services** — живые сервисы под пробой. Карточки: название, бейдж статуса, описание, стек, P50, аптайм за 90 дней, полоса истории, плашка активного инцидента. По клику раскрывается детальный вид. Сейчас здесь один сервис, `prooflayer.cloud`.
4. **Build** — данные GitHub API по всем репозиториям: последний коммит и его возраст, статус последнего прогона Actions, основной язык, число коммитов за 30 дней, полоса активности по неделям. Существует независимо от того, задеплоен проект или нет, поэтому наполняет панель настоящими данными без поднятия мёртвых сервисов.
5. **Archive** — свёрнутая группа для `discontinued`, из счётчика и аптайма исключена. Ссылки на репозитории остаются, полоса истории плоская.
6. **Incident log** — дата, сервис, тип, что случилось, что сделано, корневая причина.
7. **Work** — таймлайн ролей: слева даты и длительность, справа роль, компания, описание.
8. **Stack** — сетка из трёх колонок по группам.
9. **Contact** — инвертированный блок, крупный заголовок, ссылки.
10. **Footer** — метаданные, команда `curl`, строка о сборе данных.

### 6.1 Копирайт

Английский, плоский, фактологичный. Запрещены: «passionate», «crafting», «seamless», «robust scalable solutions», конструкции «not just X, but Y», перечисления из трёх абстрактных существительных, метафоры и олицетворение систем.

Заголовок hero: `Backend developer. Live status below, failures included.`

Лид: `Python, Django, DRF, Postgres, Celery. Currently at Floship on billing and shipping. One service is live and probed every five minutes. The rest are archived and marked as such.`

Формулировка `failures included` выбрана намеренно. Панель, показывающая реальное падение с разбором причины, доказывает инженерную практику сильнее, чем ряд зелёных точек, который никто не может проверить. Красный статус на таком заголовке перестаёт быть конфузом и становится подтверждением заявленного.

## 7. Статус-система

### 7.1 Модель данных

`data/services.json` — ручной список сервисов:

```json
[
  {
    "id": "prooflayer",
    "name": "Prooflayer",
    "blurb": "Verifiable audit trails for automated decisions",
    "url": "https://prooflayer.cloud/",
    "repo": "https://github.com/jeezdredd/prooflayer",
    "stack": ["Python", "Django", "Postgres", "Cloudflare Tunnel"],
    "monitored": true,
    "latency_threshold_ms": 400
  },
  {
    "id": "tandem",
    "name": "Tandem",
    "blurb": "Real-time synced video sessions",
    "url": null,
    "repo": "https://github.com/jeezdredd/tandem-octo",
    "stack": ["Django ASGI", "Daphne", "React", "Postgres", "Redis"],
    "monitored": false,
    "latency_threshold_ms": null
  }
]
```

Поле `url` у архивных равно `null`: адреса нет, пинговать нечего. Проба такие записи пропускает, в раздел ARCHIVE они попадают по статусу из `overrides.json`.

`data/overrides.json` — ручные оверрайды, всегда побеждают пробу:

```json
{
  "floship-portal": {
    "status": "under_maintenance",
    "note": "Scheduled window 02:00-04:00 UTC+5, billing API deploy",
    "until": "2026-09-19T04:00:00+05:00"
  },
  "old-portfolio": {
    "status": "discontinued",
    "permanence": "permanent",
    "note": "Replaced by this site in 2026"
  }
}
```

`status.json` — генерируется пробой, читается сайтом:

```json
{
  "generated_at": "2026-09-18T21:14:00Z",
  "summary": { "operational": 4, "total_monitored": 5, "uptime_90d": 99.94, "p50_ms": 41 },
  "services": [
    {
      "id": "tandem",
      "status": "operational",
      "http_code": 200,
      "latency_ms": 41,
      "p50_ms": 41,
      "uptime_90d": 100.0,
      "last_check": "2026-09-18T21:14:00Z",
      "note": null
    }
  ]
}
```

`history.json` — по 90 записей на сервис: дата, худший статус за сутки, процент аптайма, медиана времени ответа. Источник для полос.

`data/incidents.json` — ручной журнал, дополняется автоматически при срабатывании пробы на `major_outage`.

### 7.2 Правила классификации

Порядок применения, первое совпадение выигрывает:

1. `monitored: false` или `url: null` → проба пропускается, адрес не опрашивается.
2. Есть действующий оверрайд → его статус.
3. Код в диапазоне 520–530 → `major_outage`, в заметку пишется расшифровка кода.
4. Таймаут, ошибка соединения или код 5xx две пробы подряд → `major_outage`.
5. Код 2xx и время ответа больше двойного порога сервиса → `degraded_performance`.
6. Код 2xx → `operational`.

Требование двух неудачных проб подряд отсекает единичные сетевые сбои раннера, из-за которых статус мигал бы без причины. Коды 520–530 исключены из этого требования: они означают устойчивую проблему конфигурации, а не сетевой шум, и ждать вторую пробу незачем.

**Почему `third_party_error` не определяется автоматически.** Первоначально в спеке было правило «код 5xx плюс заголовок `cf-ray` → `third_party_error`». Оно неверно. Проверка `prooflayer.cloud` вернула `HTTP 530` с `server: cloudflare` и `cf-ray` — но 530 это Error 1033, то есть неподключённый туннель на стороне origin. Коды 520, 521, 522, 523, 525, 526 и 530 все указывают на origin, Cloudflare лишь сообщает о проблеме. Классифицировать их как чужую вину означало бы систематически списывать собственные падения на провайдера.

Настоящий сбой третьей стороны — это инцидент на статус-странице провайдера или 5xx от самого edge Cloudflare. Автоматически отличить это от своей поломки нельзя, поэтому `third_party_error` становится **исключительно ручным** статусом, как `partial_outage` и `under_maintenance`. Таблица в разделе 5.2 приведена в соответствие.

Расшифровка кодов для заметки к инциденту:

| Код | Расшифровка |
|---|---|
| 520 | Origin вернул неизвестный ответ |
| 521 | Origin отклонил соединение |
| 522 | Таймаут соединения с origin |
| 523 | Origin недостижим |
| 525 | Ошибка TLS-рукопожатия с origin |
| 526 | Недействительный сертификат origin |
| 530 | Error 1033, туннель Cloudflare не подключён |

### 7.3 Правила подсчёта

Знаменатель заголовка — количество сервисов, у которых `monitored: true` и статус не `discontinued`. Архивные проекты не входят ни в счётчик, ни в агрегированный аптайм: иначе закрытые проекты будут вечно тянуть общий процент вниз, хотя их просто больше не держат.

Полоса за 90 дней у архивных остаётся плоской и почти невидимой, но строка не исчезает — история работы видна и при этом не притворяется живой.

**Заголовок правой колонки** зависит от числа наблюдаемых сервисов:

- ноль наблюдаемых → `NOTHING UNDER PROBE` серым, блок SERVICES скрывается целиком
- один наблюдаемый → подпись его собственного статуса, например `MAJOR OUTAGE` цветом статуса
- два и больше → счётчик вида `N OF M OPERATIONAL`

Правило нужно потому, что при одном сервисе «1 of 1 operational» читается как отчёт ни о чём, а при падении «0 of 1 operational» выглядит как ошибка вёрстки, а не как состояние. Сейчас, с единственным живым `prooflayer.cloud`, работает вторая ветка.

**Метрики правой колонки** при малом числе сервисов дополняются данными блока BUILD, иначе сетка из четырёх клеток стоит полупустой: аптайм и P50 берутся из пробы, число коммитов за 30 дней и возраст последнего коммита — из GitHub API.

### 7.4 Блок BUILD

Источник — публичный GitHub API, токен не требуется. Данные собираются тем же Actions-воркфлоу, что и проба, и складываются в `build.json`. Сбор на стороне раннера, а не в браузере, по двум причинам: неаутентифицированный лимит в 60 запросов в час на IP посетителя выбивается мгновенно, а на раннере с `GITHUB_TOKEN` лимит 5000.

На репозиторий собирается: имя, описание, основной язык, дата и сообщение последнего коммита, вывод последнего прогона Actions, число коммитов за 30 дней, разбивка коммитов по неделям за 52 недели, число звёзд, ссылка.

Статус прогона CI рисуется теми же знаками, что и статусы сервисов, но своей шкалой: успех, провал, выполняется, не настроен. Смешивать их со статусами сервисов нельзя — это разные предметы наблюдения, и объединение читалось бы как «репозиторий лежит».

### 7.5 Производные артефакты

- `status.json` доступен публично, в футере печатается команда `curl`.
- Бейджи аптайма в формате shields для вставки в README проектов.
- `me.json` плюс разметка `application/ld+json` типа `Person` для поисковой выдачи и превью ссылок.

## 8. Телеметрия

### 8.1 Безопасность

Адрес Discord-вебхука переезжает в секрет Cloudflare Worker. Сайт шлёт данные на адрес Worker. Worker проверяет заголовок `Origin`, ограничивает частоту по IP, отбрасывает запросы с неожиданной структурой и пересылает в Discord. Работа над точностью логов начинается только после этого шага.

### 8.2 Точность

| Что | Зачем |
|---|---|
| Отсев ботов и краулеров | Сейчас превью-боты Telegram, сканеры и обходчики GitHub попадают в общий поток, из-за чего счётчик посещений не означает людей |
| Каскад geo-провайдеров | Сейчас один `ipinfo.io` без токена; упёрся в лимит — локация становится `Unknown`. Два-три провайдера с таймаутом плюс сверка с часовым поясом браузера |
| Вовлечённость | Время на странице, глубина прокрутки, просмотренные секции, клики по контактам. Отправка через `sendBeacon` на `visibilitychange`, чтобы данные не терялись при быстром закрытии вкладки |
| Разбор источника | UTM-метки и реферер. Разным ссылкам в резюме и письмах даются разные метки, видно какой канал работает |
| Дедупликация | Идентификатор сессии в `localStorage` вместо только `sessionStorage`, чтобы повторные визиты отличались от новых |

### 8.3 Приватность

**Фаза 1 — каркас.** Вёрстка, дизайн-система, лоадер, тема с инверсией, английский копирайт, удаление старых анимаций и `ambient.mp3` из критического пути загрузки. Результат можно показывать.

**Фаза 2 — статусы и build.** Actions-проба, `status.json`, `history.json`, `build.json`, карточки сервисов, раскрытие, блок BUILD, архив, журнал инцидентов, публичный эндпоинт, бейджи.

## 10. Тесты

Решение: **Vitest для чистой логики плюс тонкий набор Playwright**. npm появляется как dev-зависимость, в продакшен-бандл не попадает.

Обоснование. Самый рискованный код на сайте — не вёрстка, а расчёты: классификация ответа в статус, подсчёт аптайма за 90 дней, исключение архивных из знаменателя, детект ботов, каскад geo, разбор `status.json`. Ошибка здесь выдаёт публично неверное утверждение о работе твоих сервисов, и заметить её на глаз невозможно. Это ровно тот случай, когда юнит-тесты окупаются.

Вёрстку тестировать юнит-тестами смысла нет. Но четыре вещи ломаются молча и в юнит-тестах не видны: схлопывание лоадера на мобильной ширине, инверсия темы без вспышки не того фона, командная палитра и клавиатурная навигация, печатная версия CV. На них идёт набор из шести-восьми сценариев Playwright.

Разработка ведётся по TDD: тест на поведение пишется до реализации.

| Уровень | Что покрывает |
|---|---|
| Vitest | `status/compute.js`, `status/parse.js`, `telemetry/classify.js`, `lib/format.js` |
| Playwright | лоадер на 390 px и 1440 px, переключение темы, командная палитра, клавиатурная навигация, печатная версия, отрисовка всех восьми статусов |

## 11. Риски

| Риск | Решение |
|---|---|
| Лоадер схлопывается в линейку, привязанную к ширине колонки; на мобильной ширине линейка горизонтальная | Отдельная хореография для узких экранов, проверяется тестом Playwright на 390 px |
| Проба стучится в чужие сайты каждые 5 минут | Опрашивается только `prooflayer.cloud`. `floship.com` и `canada.ca` чужие, из списка сервисов убираются совсем и остаются в блоке WORK как места работы, а не как наблюдаемые системы |
| Единственный живой сервис лежит, панель показывает красное | Заголовок `failures included` и запись в журнале инцидентов превращают это в подтверждение практики. Но если `prooflayer` пролежит месяцами, честность превратится в небрежность: либо туннель поднимается, либо сервис переводится в `discontinued` |
| Блок BUILD выродится в мёртвую секцию, если коммитов долго нет | Возраст последнего коммита выводится явным числом дней. Секция не притворяется активной, когда активности нет |
| `status.json` коммитится каждые 5 минут | История репозитория заполняется служебными коммитами. Коммит выполняется только при изменении содержимого |
| `ambient.mp3` весит 4.7 МБ | Загружается лениво, только после явного действия пользователя; из критического пути убирается |
| 22 фичи в одном релизе не выкатываются | Разбиение по фазам, каждая фаза самостоятельно пригодна к публикации |

## 12. Открытые вопросы

- Нужен ли счётчик посетителей на самом сайте — требует KV и платного плана Worker при заметном трафике.
- Есть ли у `prooflayer.cloud` health-эндпоинт отдельно от корня. Пинг корня показывает только, отвечает ли фронт; эндпоинт, который проверяет базу и очереди, даёт осмысленный `degraded_performance` вместо бинарного «жив или мёртв».
- Останется ли `prooflayer` единственным живым сервисом. Если в течение работы появится второй, заголовок правой колонки переключится на счётчик автоматически — правило это уже предусматривает.

Закрыто 2026-09-19: health-эндпоинты для Tandem, P2P Learning и Social Platform не нужны, проекты архивные.

## 13. Критерий готовности

Фаза считается завершённой, когда: тесты уровня фазы проходят, сайт открывается без ошибок в консоли, `prefers-reduced-motion` и клавиатурная навигация работают, светлая и тёмная темы проверены, вёрстка держится на 390 px и 1440 px.
